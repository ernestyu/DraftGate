# 为什么 AI 写作需要显式状态

AI 已经可以读取很长的上下文，也能理解“这一轮只改结构”“下一步再检查证据”这样的指令。只要把前面的讨论都留在聊天记录里，模型似乎就应该知道文章做到哪里了。那么，为什么复杂长文写作还需要另外维护一份显式状态？

## 两类不同的问题

写作过程中存在两类不同的问题。第一类是内容判断，例如一个论点是否成立、某个例子是否跑题、这一段是否容易理解。这些问题没有唯一机械答案，需要模型结合上下文做语义判断。第二类是流程事实，例如某个写作阶段是否已经完成、下一步允许处理什么、当前修改应当基于哪一个文章版本。这些事实不需要“理解”，只需要准确。

如果把两类职责都留在模型上下文里，模型就同时承担了编辑者和状态机两个角色。这里的“状态机”可以理解成一份严格的进度表：当前做到哪一步，哪些步骤已经完成，下一步允许做什么。模型不仅要判断内容，还要自己记住哪些决定已经冻结、哪些步骤已经完成、当前版本是否还是上一轮确认过的版本。对一次短对话来说，这可能没有明显问题；但当文章经过多轮修改、重新打开前一步、进入新的修改轮次，或者中间出现了仓库外修改时，流程事实就可能和模型当前理解发生偏差。

## 把流程事实放到模型之外

显式 state 的作用，是把这部分确定性事实从模型内部拿出来。state 是一份机器可读的工作流记录；Gate 是一次只处理一种写作职责的阶段；cycle 是一整轮受控修改。state 可以记录当前 Gate、已经完成的 Gate、cycle、文章路径和 article revision。这里的 article revision 可以理解为文章当前版本的“版本指纹”：正文只要发生变化，对应的 Git 标识也会变化。

Git 则提供实际的版本对象。Git + structured state 只是其中一种实现，关键条件是这些流程事实由模型之外、可检查的确定性机制保存。模型仍然负责判断“文章该怎么改”，但不再需要靠自己回忆“现在到底允许改什么”。在执行下一步之前，系统可以先检查 state 和文章版本是否一致，再决定是否继续。

版本发生变化时，这套分工会更清楚。假设文章刚完成结构阶段，系统记录“下一步只能做可读性检查”。这时如果有人在仓库外改了正文，文章版本就会和 state 里记录的 revision 不一致。模型即使仍然记得“下一步做可读性”，也无法确定眼前这份文章还是不是上一轮确认过的版本。外部 state 和 Git 可以直接发现这种不一致并停止流程，避免让模型继续猜。

这种分工让流程变得可检查。模型如果想跳过当前阶段直接进入更后面的步骤，外部状态可以拒绝；文章如果在当前 Gate 之外被修改，revision 不一致可以触发停止。

某一轮已经完成后，还可以把当时的完成状态归档，并保留一个指向最终 Gate commit 的 evidence ref。archive 是这一轮结束时保存下来的状态快照；evidence ref 则像一张不可随意改写的索引卡，指向当时真实的 Git 提交。前者回答“这一轮最后是什么状态”，后者回答“这个状态究竟对应哪一个版本”。

## 外部状态能保证什么

显式状态并不证明内容本身是正确的。state 可以确认“证据检查阶段已完成”，却不能证明其中的判断一定合理；Git 可以确认文章没有被偷偷换版本，却不能判断论证是否成立。内容质量仍然来自用户、模型、证据和各个写作阶段的具体判断。外部状态解决的是另一类问题：过程有没有按约束执行，以及现在看到的结果究竟来自哪一个确定版本。

复杂长文工作流需要分开的，不只是由谁负责什么，还包括哪些事情需要语义判断、哪些事情只是确定性状态。前者适合交给模型和人共同处理，后者适合放进 Git 和结构化 state。把这两类职责拆开后，AI 写作流程才有了一个可以验证、恢复和继续执行的外部骨架。
