# 为什么 AI 写作需要显式状态

AI 已经可以读取很长的上下文，也能理解“这一轮只改结构”“下一步再检查证据”这样的指令。表面上看，只要把前面的讨论都留在聊天记录里，模型似乎就应该知道文章做到哪里了。那么，为什么复杂长文写作还需要另外维护一份显式状态？

关键在于，写作过程中其实存在两类不同的问题。第一类是内容判断，例如一个论点是否成立、某个例子是否跑题、这一段是否容易理解。这些问题没有唯一机械答案，需要模型结合上下文做语义判断。第二类是流程事实，例如 G3 是否已经完成、下一步允许执行哪一个 Gate、当前修改应当基于哪一个文章版本。这些事实不需要“理解”，只需要准确。

如果把两类职责都留在模型上下文里，模型就同时承担了编辑者和状态机两个角色。它不仅要判断内容，还要自己记住哪些决定已经冻结、哪些步骤已经完成、当前版本是否还是上一轮确认过的版本。对一次短对话来说，这可能没有明显问题；但当文章经过多轮修改、reopen、不同 cycle，或者中间出现了仓库外修改时，流程事实就可能和模型当前理解发生偏差。

显式 state 的作用，就是把这部分确定性事实从模型内部拿出来。以一个分阶段写作流程为例，state 可以记录当前 Gate、已经完成的 Gate、cycle、文章路径和 article revision。Git 再提供对应的版本标识。这样，模型仍然负责判断“文章该怎么改”，但它不需要靠自己回忆“现在到底允许改什么”。在执行下一步之前，系统可以先检查 state 和文章版本是否一致，再决定是否继续。

这种分工带来的直接好处，是流程变得可检查。模型如果想从 G3 直接跳到 G5，外部状态可以拒绝；文章如果在当前 Gate 之外被修改，revision 不一致可以触发停止；某一轮已经完成后，archive 和 evidence 也可以保留当时的状态和文章版本。这里的重点不是让模型更聪明，而是让它不再单独承担那些本来可以由确定性系统处理的事实。

同样重要的是，显式状态并不证明内容本身是正确的。state 可以确认“G5 已完成”，却不能证明 G5 的判断一定合理；Git 可以确认文章没有被偷偷换版本，却不能判断论证是否成立。内容质量仍然来自用户、模型、证据和各个 Gate 的具体判断。外部状态解决的是另一类问题：过程有没有按约束执行，以及现在看到的结果究竟来自哪一个确定版本。

因此，复杂长文工作流真正需要分开的，不只是“人做什么、AI 做什么”，还包括“哪些事情需要语义判断、哪些事情只是确定性状态”。前者适合交给模型和人共同处理，后者适合放进 Git 和结构化 state。把这两类职责拆开后，AI 写作流程才有了一个可以验证、恢复和继续执行的外部骨架。
