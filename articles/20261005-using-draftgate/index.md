# DraftGate 使用说明（暂定）

很多人第一次用 AI 写文章时，会觉得事情应该很简单：把自己的想法、材料和要求告诉模型，它就应该能够直接给出一篇完整文章。对于需要多轮判断、结构控制和证据边界的长文，这种做法很容易暴露问题。主旨可能漂移，结构可能松散，例子和论点之间的关系也可能不稳定；让模型修改一个地方，它还可能顺手改动已经确定的部分。于是另一种做法出现了：不断增加 prompt、writing skill 和写作规则，希望靠一套更复杂的说明，让 AI 一次把文章写好。但规则变多，并不会自动让复杂写作变得可控。

本文要回答的问题是：**怎样用 DraftGate，把 AI 辅助写作从一次难以控制的“整篇生成”，变成一个人可以逐步讨论、判断、修改和验证的过程？**

核心判断是：对于需要反复判断、修改和核查的复杂长文，human-in-the-loop 仍然很重要，也就是人在整个写作过程中持续参与关键判断，而不是把主题交给 AI 后等待最终成品。AI 可以参与讨论、提出思路、寻找反例、核查事实和证据，也可以帮助组织结构和修改表达，但文章的关键判断仍然需要人持续参与。DraftGate 做的事情，是把这些不同性质的写作职责拆成 G1–G7 七个阶段，每个 Gate 只处理一种问题。它再用 Git state 记录文章当前进行到哪一步，并用 CI（持续集成检查）在每次提交后自动验证 Gate 顺序、state 是否匹配以及状态转移是否合法。这样，流程控制不需要依赖 AI 自己记住“现在做到哪里”。

本文重点是 DraftGate 的实际使用，不展开抽象的 AI 写作方法论。进入 G1 之前的开放讨论也属于真实使用过程：先通过 brainstorm 让主题、动机和大致方向成形，再进入受状态控制的 G1–G7。后文会以这篇文章本身作为贯穿案例，实际走完这套流程。本文的主线限定为“怎样实际使用 DraftGate”：教程必须交代使用前准备、Pre-G1 brainstorm，以及 G1–G7 的逐步执行；每到一个 Gate，都先说明这一阶段解决什么问题，再停下来检查它实际修改了什么、state 如何变化、CI 是否通过，然后才进入下一步。前面对“一次性生成”和“复杂 writing skill 为什么仍会失败”的讨论只用于解释为什么需要这套流程，不扩展成独立的方法论主线；更广的 Agent 架构、Prompt Engineering 理论、CMS 和发布系统也不属于本文范围。

## 1. 为什么需要把写作拆成多个阶段

先解释教程的起点：对于需要多轮判断的复杂长文，一次性生成和把大量规则塞进一个 writing skill，为什么仍然可能难以稳定控制，以及 human-in-the-loop 为什么仍然重要。这里的作用只是说明后面的流程为什么存在，不扩展成独立的方法论讨论。

## 2. 使用前准备

实际使用从注册并登录 GitHub、fork DraftGate 开始。fork 可以理解为在自己的 GitHub 账户下复制一份独立仓库，之后的文章、state 和提交都发生在自己的副本里，不会修改原始 DraftGate 仓库。接下来，把这个 fork 后仓库的链接交给能够读取和修改 GitHub 的 ChatGPT 或其他 AI Agent。Agent 指能够读取仓库文件、修改文件并提交 Git 变更的 AI 工具。最后确认 GitHub Actions 可以运行；它会在 GitHub 托管的 runner 上自动执行 DraftGate 的验证脚本。完成这些准备后，后续流程所需要的仓库、版本和 CI 环境就已经建立。

## 3. Pre-G1：先把想法讨论清楚

进入 state control 之前先进行开放 brainstorm。这里可以发散、换角度、推翻原来的设想，也不要求 PASS。Pre-G1 不写入 workflow state，因为这一阶段的目标恰恰是保持开放。等到用户已经能大致说明为什么想写这篇文章、想讨论什么、希望回答什么，再进入 G1，开始受控流程。

本文自己的案例也从这里开始：最初只是“写一篇 DraftGate 教程”，经过讨论后才明确教程要从一次性生成的问题引入，并把 human-in-the-loop、G1–G7、state 和 CI 连成一条完整使用路径。

## 4. 正式进入 DraftGate：G1–G7

从 G1 开始进入受状态控制的 workflow。state 是一个 JSON 文件，记录当前 Gate、已经完成的 Gate、文章对应的 Git revision 以及流程是否完成。后面的每个 Gate 都按同一方式讲解：先说明它解决什么问题，再执行，并停下来检查文章修改、state 变化和 CI 结果。这样读者看到的不只是规则说明，还能看到一次真实执行如何改变文章和流程状态。

### G1 — Main Question & Thesis

确定文章真正要回答的问题和核心判断。本文在 G1 冻结了“怎样用 DraftGate 把整篇生成变成逐步可控过程”这一主问题。

### G2 — Scope & Branch Control

确定哪些内容属于教程主线，哪些只能作为背景、机制说明或排除范围。本文在 G2 冻结了准备、Pre-G1、G1–G7 实操三部分，并把更广的 Prompt Engineering、Agent 架构和发布系统排除在外。

### G3 — Argument Architecture

决定文章如何推进，并建立统一的 Explanatory Spine。本文以 question-driven 为 primary driver，同时让这篇文章自身的写作过程作为贯穿 case。

### G4 — Reader Accessibility

检查读者是否能够理解重要概念、机制和局部类比，不用额外背景知识也能跟上文章。

### G5 — Claim & Evidence Boundary

检查关键判断是否写得过强、证据是否足够、是否存在合理的替代解释或反例。

### G6 — Paragraph Organization

按语义和论证职责整理段落，避免把一个论证动作切碎，也避免把几个不同职责硬塞进同一段。

### G7 — Final Language & Pattern Audit

在前面各层已经冻结后做最终语言清理，检查重复、机械 signposting、固定节奏和其他模板化写作模式，不再重做前面的结构判断。

## 5. 回看：DraftGate 实际控制了什么

回看完整流程：人的判断从 Pre-G1 开始进入写作，G1–G7 把不同职责分开，Git state 记录当前阶段，CI 在模型之外检查执行顺序和状态转移。可以把这三层理解为：人负责判断，AI 负责讨论和编辑，Git/CI 负责记账和验收。教程到这里再回答开头的问题：DraftGate 的价值不在于让 AI 自动写完一篇文章，而在于让人能够持续控制 AI 辅助写作的过程。
